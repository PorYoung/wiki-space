01现状诊断：三个缺陷 + 两个 P0 漏洞

三处缺陷共同指向同一件事："团队"这个词在数据模型里不存在。可见性的"团队"档位没有实体可依赖，只能退化成一个空承诺。

缺陷 1 · 无团队实体

用户无法创建团队

现状真相

"团队"页面实际是全平台用户表：GET /api/v1/team 直接 select … from users limit 200，把 globalRole 映射成 Owner/Editor 假角色；"邀请"= 凭空创建平台账号；"改角色"= 改全局权限。

目标形态

新增 teams + team_members（类 GitLab Group，不做嵌套）；任何登录用户可建团队，成员角色 owner / maintainer / member，团队成为文档库的归属主体。

缺陷 2 · 无归属选择

用户无法决定文档归属

现状真相

文档库只有 owner_id（恒 = 创建者），建库入口没有归属参数；库创建后无法把资产交给团队——只能靠逐个邀请成员，人走权限散。

目标形态

projects.owner_type ∈ {user, team} + owner_team_id。建库时选择归属；库设置页支持「个人 ⇄ 团队」转移，带前置条件校验与审计。

缺陷 3 · 三态失控

可见性档位名不副实

现状真相

服务端 team 与 public 语义完全等价——都是"任何已登录用户可读"；写权限恒需逐库成员。用户以为收敛到了团队，实际是全站。

目标形态

五态：private / team-read / team-write / public-read / public-write。范围与能力解耦，有效权限 = 显式成员角色 ∪ 团队/公开档位（并集语义）。

⚠ 附带发现：两个 P0 越权漏洞（随本方案先行止血）

S1 PATCH /api/v1/team/:id/role 无任何权限校验，且逻辑为 role='Owner' → globalRole='admin'，只阻止自降级、不阻止自升级——任何登录用户可把自己提为全局 admin。管理端同类端点有守卫（routes-platform.ts:640,700）。
S2 POST /api/v1/team/invite 无校验，可直接 INSERT users 批量造账号，污染审计与成员目录。
S3 GET /api/v1/team 无校验的 200 条用户枚举（含 email / globalRole）。

处置：B0 批次三端点先加 requireAdmin 止血，B1 随团队页重构删除收敛（spec §7）。

02权限矩阵：五态 × 九类身份

有效权限 = 显式成员角色 ∪ 团队隐式档位 ∪ 公开档位（并集语义，与 GitLab 一致）。切换维度查看每种能力的真实边界——全部组合由单测 U1 逐条锁定（200 组）。

✓ 允许 — 拒绝
身份 \ 可见性 私有private 团队·只读team-read 团队·可写team-write 公开·只读public-read 公开·可写public-write

匿名（未登录）行在所有档位均为拒绝：本期维持"全档位登录态"边界，匿名访问面仅已发布站点 /sites/:slug。
两条不变式：① 写能力的三个来源取并集——显式写角色 ∪「团队成员 + team-write」∪「public-write」；非团队成员的 guest 在 team-write 库上只读，若其同时是团队成员则可写（并集），要真正限制请移出团队或降档位；② 管理 / 删除以可读为前提，且 私有档严格隔离——团队 owner / maintainer 对"私有"团队库不可见也不可管（兜底 = 全局 admin，见 spec §11-8）。

04落地路线：B0 止血 → B1 主体 → B2 收敛

每批次的完成标准（DoD）均可自动验证：单测 200 组合矩阵 + e2e P10a–P10n 断言段。

B0

安全止血

独立于功能，先堵两个 P0 越权与用户枚举。

  • S1/S2/S3 三端点加 requireAdmin（最小 diff，前端不破）
  • TeamPage 对 403 优雅降级为"仅管理员可访问"空态
  • 越权回归用例固化（P10m），防回潮
DoD 普通用户调用三端点全部 403；admin 原行为不变；e2e 全绿。
