## 1. 背景与目标

### 1.1 产品定位的两个核心场景

ewiki 的产品价值覆盖两个互补的使用场景：

| 场景 | 定位 | 典型用户 | 核心诉求 |
| --- | --- | --- | --- |
| **云端 Wiki 共享** | 团队知识协作平台（当前主线） | 团队负责人、维护者、所有成员 | 多源接入、统一检索、协同编辑、权限管理、一键发布 |
| **本地知识维护** | 个人/桌面知识管理工具（远期桌面客户端） | 个人知识管理者、离线工作者 | 本地文件直读、离线可用、性能优先、按需同步到云端 |

两个场景不是割裂的，而是**同一数据模型在不同部署形态下的表现**：用户在本地积累的知识，可以平滑地"晋升"为团队共享的云端 Wiki；云端 Wiki 的内容也可以"下沉"到本地供离线使用。

### 1.2 设计原则

1. **数据模型统一**：云端和本地使用相同的文档模型（Document / Project / Source），同步仅为数据传输层差异
2. **本地优先（Local-First）**：桌面客户端默认本地读写，云端同步是后台行为，不阻塞用户操作
3. **渐进式同步**：用户可选择哪些项目同步、哪些仅本地存在；同步是能力，不是强制
4. **冲突可解释**：冲突发生时提供清晰的双方对比与裁决选项，策略与在线模式一致（PRD F43）
5. **离线可用**：断网时核心功能（浏览、编辑、搜索）100% 可用，联网后后台静默同步

## 3. 方案选型对比

### 3.1 同步方案选型

| 方案 | 原理 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| **Git 协议同步** | 以 Git 为事实来源，两端都是 Git 工作副本，通过 pull/push 同步 | 成熟可靠、冲突处理工具链完善、历史完整 | 二进制文件支持弱、大仓库性能差、学习成本高 | 技术团队、文档以 Markdown 为主 |
| **CRDT 实时同步** | 基于 Yjs 的 CRDT 算法，操作级合并 | 自动合并、冲突率低、实时性好 | 历史回溯复杂、存储开销大、需要持续连接 | 多人实时协作、短文档频繁编辑 |
| **增量快照同步** | 按文档粒度记录版本向量，传输增量 diff | 实现简单、与现有数据模型兼容 | 冲突需要人工介入、实时性一般 | 个人知识同步、低并发团队场景 |
| **混合方案（推荐）** | 文档内容走 CRDT（Yjs），文件结构走 Git；同步时按文档粒度合并 | 兼顾实时协作与版本管理能力、渐进式迁移 | 架构复杂、需要维护两套同步逻辑 | ewiki 双场景目标 |

### 3.2 推荐方案：文档级 CRDT + 项目级 Git

**核心理念**：不同粒度使用不同同步策略

- **文档内容层**：使用 Yjs CRDT 同步（已有协作编辑基础）
  - 每篇文档是一个独立的 Yjs Doc
  - 同步时传输 Yjs update 增量
  - 自动合并冲突，无需人工干预

- **项目结构层**：使用 Git 同步（已有 git package 基础）
  - 目录结构、文件重命名、删除操作走 Git
  - 完整的版本历史和分支能力
  - 大文件（图片、附件）走 Git LFS 或对象存储直传

- **同步编排层**：统一的 SyncEngine 协调两者
  - 检测网络状态，自动调度同步
  - 冲突降级策略（CRDT 自动合并 > Git 三向合并 > 人工裁决）
  - 同步进度与状态可视化

### 3.3 本地存储选型

| 方案 | 优点 | 缺点 | 推荐度 |
| --- | --- | --- | --- |
| **SQLite + 本地文件系统** | 生态成熟、事务支持好、全文搜索（FTS5）、可嵌入 | 多进程并发有限制 | ★★★★★ |
| **IndexedDB（Web 版本地）** | 浏览器原生、无需安装 | 容量限制、性能较差、仅 Web | ★★★ |
| **DuckDB** | 分析查询性能强、列式存储 | 事务支持弱、生态不如 SQLite | ★★ |

**推荐**：桌面端使用 SQLite（FTS5 全文搜索）+ 本地文件系统（Git 工作副本）。

## 4. 功能映射与差异

### 4.1 云端 vs 本地功能矩阵

| 功能模块 | 云端 Wiki | 本地知识（桌面端） | 说明 |
| --- | --- | --- | --- |
| 项目管理 | ✅ 完整 | ✅ 本地项目 | 本地项目默认不同步，用户可主动开启 |
| 文档浏览 | ✅ | ✅ 离线可用 | 同一渲染引擎 |
| 文档编辑 | ✅ 实时协同 | ✅ 离线编辑 | Yjs 为共享底座 |
| 全文搜索 | ✅ PG ILIKE → Meilisearch | ✅ SQLite FTS5 | 搜索接口统一，实现适配 |
| 数据源接入 | ✅ 4 类源 | ✅ 本地文件夹优先 | 本地源=桌面端一等公民 |
| Git 同步 | ✅ | ✅ 双向同步 | 共享 git package |
| 成员管理 | ✅ | ⚠️ 仅同步项目可见 | 本地端无成员概念 |
| 权限控制 | ✅ 4 级角色 | ➖ 无 | 本地即所有者 |
| 发布站点 | ✅ | ⚠️ 需联网推送 | 本地可预览，发布走云端 |
| AI 智能整理 | ✅ 服务端 | ⚠️ 可选本地模型 | 按部署配置切换 |
| 关系图谱 | ✅ | ✅ | 纯前端计算，两端一致 |
| 通知中心 | ✅ | ⚠️ 仅同步相关 | 本地端无团队通知 |
| 主题外观 | ✅ 8 套 | ✅ 8 套 | 完全共享 |

### 4.2 桌面端特有功能

1. **全局快捷搜索**：系统级热键唤起搜索面板（类 Alfred / Raycast）
2. **文件系统监听**：实时监听本地文件夹变化，自动导入/同步
3. **Markdown 编辑器增强**：支持 Vim 模式、双栏编辑、本地图片拖拽
4. **CLI 命令行工具**：`ewiki sync`、`ewiki search`、`ewiki publish` 等命令
5. **系统托盘**：后台同步状态、快捷入口、未读通知角标
6. **多知识库挂载**：可同时挂载多个本地文件夹作为独立知识库

## 5. 同步协议设计

### 5.1 同步状态机（扩展）

在现有 PRD 6.3 状态机基础上，增加桌面端本地状态：

```
           ┌─────────────┐
           │  untracked  │  本地新文档，未关联云端
           └──────┬──────┘
                  │  推送到云端
           ┌──────▼──────┐
   ┌───────►   synced    ◄───────┐
   │       └──────┬──────┘       │
   │              │               │
 云端更新     本地编辑         冲突解决
   │              │               │
   │       ┌──────▼──────┐        │
   │       │  modified   │        │
   │       └──────┬──────┘        │
   │              │               │
   │       拉取云端更新            │
   │              │               │
   │       ┌──────▼──────┐        │
   └───────┤   conflict  ├────────┘
           └─────────────┘
```

### 5.2 同步策略选项

用户可为每个项目选择同步策略：

| 策略 | 行为 | 适用场景 |
| --- | --- | --- |
| **仅本地** | 不同步到云端，数据只在本地 | 个人草稿、敏感信息 |
| **手动同步** | 用户主动点击"同步"才上传/下载 | 网络受限、流量敏感 |
| **Wi-Fi 自动同步** | 仅在 Wi-Fi 环境下自动同步 | 笔记本移动场景 |
| **实时同步** | 变更后立即同步（类云端体验） | 稳定网络、团队协作 |

### 5.3 冲突解决策略

与 PRD F43 保持一致，桌面端增加本地特有选项：

- **保留我的**（本地优先）
- **以远端为准**（云端优先）
- **每次询问**（弹出对比面板）
- **智能合并**（Yjs CRDT 自动合并，默认推荐）

## 6. 数据迁移路径

### 6.1 本地 → 云端（晋升）

1. 用户在本地项目上点击"发布到团队"
2. 选择目标团队 / 创建新项目
3. 全量上传文档内容 + 历史版本
4. 设置项目可见性与成员
5. 完成后项目变为"同步项目"，后续变更双向同步

### 6.2 云端 → 本地（下沉）

1. 用户在云端项目列表中点击"保存到本地"
2. 选择本地存储位置
3. 后台全量下载（可设置仅下载元数据，内容按需拉取）
4. 下载完成后可离线访问
5. 本地编辑后可选择是否推送回云端

### 6.3 渐进式采用路径

```
个人用户（仅本地）
    │
    ▼  积累知识后
团队成员（云端协作 + 本地缓存）
    │
    ▼  团队壮大后
团队管理员（完整云端管理能力）
```

## 7. 技术实施路线

### 7.1 Phase 1：基础铺垫（当前可并行）

- [ ] 抽离 `@ewiki/core` 包：将纯业务逻辑从 server 中剥离，可在 Node.js 和 Electron 中运行
- [ ] 统一 Storage 接口：抽象 BlobStore，支持本地文件系统和对象存储两种实现
- [ ] 搜索服务接口化：SearchService 接口已有，补充 SQLite FTS5 实现
- [ ] Yjs 文档持久化优化：确保文档内容可序列化为标准格式（Markdown + Yjs update）

### 7.2 Phase 2：桌面客户端 MVP

- [ ] Electron 壳层 + 本地 SQLite 初始化
- [ ] 本地项目创建与文档管理（不依赖云端）
- [ ] 本地全文搜索（SQLite FTS5）
- [ ] 本地文件夹源接入（文件系统 watcher）
- [ ] 与云端的单向同步（拉取）

### 7.3 Phase 3：双向同步

- [ ] SyncEngine 实现（文档级 CRDT + 项目级 Git）
- [ ] 冲突检测与解决 UI
- [ ] 同步状态可视化
- [ ] 离线编辑 → 联网自动合并

### 7.4 Phase 4：桌面端增强

- [ ] 全局快捷搜索（系统热键）
- [ ] CLI 工具
- [ ] 系统托盘与通知
- [ ] 本地 AI 模型集成（可选）

## 8. 风险与应对

| 风险 | 影响 | 概率 | 应对措施 |
| --- | --- | --- | --- |
| CRDT 与 Git 双同步复杂度高 | 开发周期延长 | 中 | Phase 2 先用 Git 同步跑通，CRDT 作为 Phase 3 增强 |
| 桌面端性能问题（大知识库） | 用户体验差 | 中 | 虚拟滚动、懒加载、SQLite 索引优化 |
| 冲突数据丢失 | 用户信任受损 | 低 | 所有冲突保留双方完整版本，自动备份 |
| 多端同时编辑的数据一致性 | 内容错乱 | 低 | Yjs CRDT 保证最终一致性 |
| 本地数据安全（丢失/损坏） | 数据丢失 | 中 | 自动本地快照 + 云端备份选项 |
